# qac iter-5d — RLCC workflow materialization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** At run-create, fetch the operator's picked RLCC workflow from `rlccclient` and inline the full `{name, source_sha, actions[]}` snapshot into `RunCreated.payload.rlcc_workflow`. Flip `firmware-release-canary.yaml`'s `rlcc_workflow` input from `required:false` to `required:true`. Backend-only Go plus seed/integ/MSW touchups.

**Architecture:** Inlined-snapshot approach (Option B from spec §2) — the canary template's spine stays the interpretation framework; the workflow informs what the L-steps do, not what shape the run has. Freeze-at-start semantics: in-flight runs walk the snapshot taken at run-create, even if the chart changes upstream. Single new step in `createRunHandler` between `ValidateInputs` and `runID` generation: resolve workflow, fail loud (no half-baked events) if missing or action-empty, build snapshot, inline into payload. No new event kinds, no new column, no new migration. Backward compat by design: pre-iter-5d runs decode cleanly (omitempty pointer round-trips); engine projector ignores the new field; iter-5e's `rlcc_action_probe` will read it.

**Tech Stack:** Go 1.26.3 (bare `qac` module), stdlib only beyond what iter-5a/5b already pull. Frontend code untouched — only MSW fixture data needs the template version + required-flag bump to mirror the backend.

### Task 1: `WorkflowSnapshot` value type in `rlccclient/types.go`

**Why first:** every subsequent task references this type. Land the type with its JSON round-trip test before anything else.

**Files:**

🟦 **Go learning beat — value types vs reference types.** `WorkflowSnapshot` is a *value type* (struct, not pointer). When we later store it inside `RunCreatedPayload`, Go copies the struct's three fields. Two of those fields are scalar strings (`Name`, `SourceSHA`); the third is `[]Action` — and a slice in Go is a *24-byte header* (pointer, length, capacity) that points at a backing array. Copying the slice copies the header but the backing array stays shared until something mutates it. We never mutate, so no copy cost worth worrying about. Same pattern iter-5b's `BMNDiscoveredPayload.BMNs []BMN` uses.

**Why next:** store decodes RunCreated.payload to drive the runs-table UPDATE (template_id, bundle, rack, inputs). **Files:**

- Test: `internal/store/events_test.go` (extend if file exists; else create — check first)

🟦 **Go learning beat — `json.RawMessage` as a passthrough.** `json.RawMessage` is `[]byte` under the hood, but with custom `MarshalJSON`/`UnmarshalJSON` methods that pass the bytes through unchanged. It's the Go idiom for *"decode this part of the JSON later, or not at all."* Here, the store doesn't care what's inside `rlcc_workflow` — it just wants the field to round-trip cleanly through the SQLite `payload` TEXT column. Using `*json.RawMessage` instead of `*WorkflowSnapshot` saves the import cycle headache and the parse cost.

🟦 **Go learning beat — `omitempty` on pointer-to-struct.** A `*X` field with `omitempty` JSON tag has three states: nil (omitted from output), non-nil pointing at zero value (included with zero fields), non-nil pointing at populated value (included fully). When *decoding* a JSON missing the field, the pointer stays nil — exactly what we want for pre-iter-5d rows.

🟦 **Go learning beat — sentinel error pattern with `errors.Is`.** `rlccclient.ErrWorkflowNotFound` is a *package-level sentinel* (`var ErrWorkflowNotFound = errors.New("...")`). The idiomatic way to ask *"is this specific error?"* is `errors.Is(err, rlccclient.ErrWorkflowNotFound)`. It walks the error chain (set up via `fmt.Errorf("%w: ...", sentinel)`) looking for the sentinel. Beats string-matching on `err.Error()` — string matches are brittle and tie the caller to the message format. iter-5b's `lifecycleclient.ErrAuth` follows the same pattern.

🟦 **Go learning beat — all-or-nothing handler semantics.** The handler validates inputs (existing `ValidateInputs`), then resolves the workflow (new), then resolves racks → BMNs (existing iter-5b), THEN starts emitting events. If anything fails before the first `AppendEvent` call, the response is a 4xx with zero events written. No half-baked run lands in the log. iter-4a set this pattern; iter-5b extended it; iter-5d adds one more guard before the line.
